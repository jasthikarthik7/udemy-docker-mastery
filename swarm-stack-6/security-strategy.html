For the Team

A Few Principles to Work By

A new team brings energy, ideas, and ambition. These principles are here to keep us grounded — focused on what delivers real value, built on what already works, and honest about what we're here to do.

02
01
Tangibles before exploration
A new team generates ideas fast — that's a strength. But value is proven through delivery, not exploration. This framework is a long-term strategy we mature toward, not a backlog we build all at once.
Ship one working pattern that proves the concept before expanding scope. A real test against a real service is worth more than ten designs on a whiteboard.
02
Buy beats build — for solved problems
Tenable and Noname are battle-tested, vendor-maintained, and continuously evolving. Building a replacement for what they already do well is expensive to create and expensive to maintain over time.
When a tool already solves the problem, use the tool — and use it well. Our job is not to replicate their capabilities, it's to make them more effective as part of a coherent strategy.
03
Build only to fill real gaps
TISA exists for the specific things tools can't do: validating controls against your threat model, proving past incidents can't recur, testing that critical business workflows are protected across every deploy.
Every pattern we build should close a gap in the overall security strategy — not a gap in our tool knowledge. If there's no signal source, there's no pattern. Build with evidence, not enthusiasm.
The Problem

Why Build-Blocking Alone Fails

Traditional AppSec pipelines create friction without proportional risk reduction. Teams learn to ignore alerts, suppress findings, or bypass gates entirely.

03

🚫 The Old Model

  • SAST/SCA as hard gates — every critical finding blocks the build regardless of exploitability or context
  • Alert fatigue — hundreds of findings, most theoretical, no signal-to-noise filtering
  • Left-only thinking — static tools can't validate whether controls actually work at runtime
  • No business context — a critical finding in dead code blocks the same as one in your payment flow

⚠️ The Consequences

  • Developer distrust — "just add a suppression comment" becomes the default response
  • Compliance theater — tools running but findings not actioned
  • Coverage gaps — incidents keep happening in areas the static tools missed
  • No incident feedback loop — post-incident learnings never become regression tests
  • TAM threats not validated — threat models exist in Confluence, not in CI/CD
Core gap: There is no layer that takes a threat, an incident, or a critical finding and asks: "Is the control that should prevent this actually working in production?" — and does it continuously, without blocking velocity.
The Vision

Continuous Security Assurance

Move from reactive gates to a continuous, evidence-based assurance model where every control has a test, and every risk has a validated mitigation status.

04
Principle 1

Threat-Informed

Every test case traces back to a threat (TAM), a finding (SAST/SCA), or a real incident. No test exists without a risk owner.

Principle 2

Control-Validated

We don't just detect vulnerabilities — we continuously verify that the controls meant to prevent them are functioning as designed.

Principle 3

Non-Blocking by Default

Build velocity is preserved. Blocking is reserved for critical business workflow failures and confirmed exploitable CVEs — not theoretical risk.

Addressing the Team

"Can't We Just Use DAST / Noname?"

Honest answer: there is real overlap — roughly 30–40%. But the 60–70% that DAST and API security tools cannot cover is exactly where incidents keep recurring.

06
❌ Where DAST Falls Short
  • No memory of your incidents — DAST crawls generically; it has no knowledge of your 2024 SQLi or IDOR incident
  • No threat model context — Noname doesn't know TAM-042 says "attacker bypasses checkout via BOLA"
  • Can't validate business logic — a 5-step checkout flow's authorization integrity requires knowing your semantics
  • Finds new issues, not regressions — if a post-incident control silently drifts, DAST won't notice
✅ What Tenable & Noname Own — Let Them
Tenable (DAST)
  • Injection & web app scanning — SQLi, XSS, command injection across all endpoints
  • Broad vulnerability discovery — crawls and finds unknown issues TISA won't
Noname (API Security)
  • API discovery & inventory — finds shadow and undocumented APIs via traffic analysis
  • CORS, rate limiting, schema drift — runtime API posture and OpenAPI conformance
  • Sensitive data exposure — detects PII/secrets leaking in API responses
TISA explicitly does NOT duplicate these.
★ TISA Owns the 3 Gaps
🔥 Incident Regressions
Replay exact past incident scenarios on every deploy. No other tool does this.
🎯 TAM Threat Validation
Confirm that each assumed mitigating control in your threat model is actually enforced.
🛒 Workflow Integrity
Multi-step business flow security assertions that require knowing your domain logic.

Signal Sources

What Drives TISA Test Cases

Every TISA test must trace to a concrete signal. No signal, no test. This keeps the library lean, high-fidelity, and business-relevant.

07
Signal Source What It Provides Example TISA Test Generated Priority
🔥 Past Incidents
 Exact attack scenario, affected endpoint, root cause Replay the incident scenario as an automated regression test that must pass in every deploy P0
🎯 TAM Threats
 Threat actor, attack vector, target asset, assumed control Validate that the assumed mitigating control (e.g., rate limiting, auth check) is implemented and enforced P1
🛒 Critical Workflows
 Business flows where integrity failure = direct impact (checkout, auth, payments, data export) End-to-end security assertions on workflow steps: authorization at each step, no privilege escalation, correct data scoping P1
🔍 SAST Criticalities
 Confirmed-exploitable high/critical findings in production code paths Dynamic validation that the exploitable code path is actually reachable and the input is unsanitized at runtime P2
📦 SCA / CVEs
 CVSS 9+, with PoC exploit available, in a direct dependency Probe test confirming the vulnerable code path is either unreachable, patched, or compensating control is active P2
🔍 SAST / SCA Criticals
 Confirmed-exploitable CVSS 9+ finding in a production code path that DAST (Tenable) may not exercise during its crawl Targeted exploitability probe — exercises the exact flagged endpoint/parameter to confirm the vulnerability is reachable and unsanitized at runtime. Not a re-scan. P2
🏭 Compliance Controls
 PCI-DSS, SOC2, HIPAA control requirements Control validation test asserting the technical control exists (e.g., encryption at rest, audit logging, access review) P3
Why SAST/SCA criticals belong here too: Tenable fuzzes broadly but may never hit the exact code path SAST flagged. A TISA probe targeted at the specific endpoint and parameter SAST identified is more precise than hoping DAST's crawl covers it — and it runs in under 10 seconds.
The Middle Layer

TISA Test Taxonomy — The 4 Focused Areas SCOPED

TISA deliberately covers only what DAST and API security tools cannot. A lean library of 30–50 high-signal tests beats 500 noisy ones every time.

08
🔥 Area 1 — Incident Regressions

Every past incident becomes a permanent, automated regression test. If the fix drifts, CI/CD catches it before production does.

  • Exact payload replay — the specific request that exploited you must now be blocked
  • Control persistence check — the post-incident control is validated on every deploy
  • Hotfix survival test — emergency patches confirmed to survive dependency updates
  • WAF rule validation — rules added post-incident are still active and enforced
Signal source: Incident post-mortem tickets (Jira, PagerDuty)
SLA to add test: 48h from incident close
🎯 Area 2 — TAM Threat Validation

For each TAM P0/P1 threat, there is an assumed mitigating control. TISA validates that control is actually implemented and not theoretical.

  • Auth bypass probes — TAM assumes auth gate; TISA confirms it rejects unauthorized requests
  • Privilege boundary checks — TAM assumes role separation; TISA confirms vertical escalation is blocked
  • BOLA / IDOR per threat — TAM assumes scoped data access; TISA validates with real user contexts
  • Session control assertions — TAM assumes session invalidation; TISA confirms logout is effective
Signal source: TAM export (STRIDE / PASTA / threat model doc)
Coverage target: 100% of P0, 80% of P1 threats
🛒 Area 3 — Workflow Integrity

Critical business flows (checkout, auth, payments, data export) must maintain security invariants across every step. DAST cannot encode these — only you can.

  • Step-by-step authZ — authorization re-validated at each workflow stage, not just entry
  • Cross-user isolation — user A's session cannot touch user B's workflow state
  • State manipulation — skipping steps or replaying steps is detected and rejected
  • Data scoping — responses contain only data the authenticated user owns
Signal source: Product/engineering workflow documentation
Coverage target: All P0 business flows instrumented
🔍 Area 4 — SAST/SCA Exploitability Probes P2

Tenable fuzzes broadly but may never hit the exact path SAST flagged. A targeted runtime probe confirms the specific finding is actually reachable and exploitable — not theoretical.

  • Reachability confirmation — exercise the exact endpoint/parameter SAST identified, not a generic fuzz
  • Input sanitization probe — confirm user-controlled input reaches the flagged sink unsanitized
  • CVE path reachability — confirm a CVSS 9+ dependency is actually invoked in the production code path
  • Compensating control check — if SCA finding is accepted risk, confirm the compensating control is active
Signal source: SAST triage (confirmed exploitable only) + SCA CVSS 9+ with PoC
Scope guard: Only when Tenable is unlikely to exercise that specific path
What TISA does NOT do: Generic injection fuzzing, CORS checks, rate limit validation, API schema drift — these belong in Tenable and Noname. Keeping TISA narrow is what makes it maintainable.
Test structure: Each test carries risk_id (TAM ID, incident ticket, or SAST finding ID), area (regression | threat | workflow | probe), and gate (hard_block | sla_tracked). No test without a risk owner.
Gating Strategy

Softened Gates with Risk-Based SLAs

Replace binary block/pass with a three-tier gating model. Only confirmed, business-critical failures stop a deployment. Everything else enters a tracked backlog with SLA timers.

09
🛑
HARD BLOCK

Deployment blocked immediately

TISA test fails on a critical business workflow (auth, checkout, payments, data access) or confirmed-exploitable CVSS 10 in a reachable direct dependency with active public PoC. TAM P0 threat with no mitigating control.

~2–5% of findings
⏱️
SLA GATE

Deploy proceeds — ticket created with SLA timer

High-severity SAST/SCA findings (non-critical workflows), TAM P1/P2 threats, TISA test failures on non-critical paths, DAST high findings. SLA: 72h (critical) / 7d (high) / 30d (medium). Missed SLA triggers escalation and eventual block.

~20–30% of findings
✅
INFORMATIONAL

Deploy proceeds — tracked in risk dashboard

Low/medium SAST findings, low CVSS CVEs, DAST informational findings, compliance drift (non-urgent). Surfaced in the posture dashboard for quarterly review. No ticket created automatically.

~65–75% of findings
Leadership talking point: This model reduces meaningless blocks by ~80% while increasing coverage of real business risk. We're trading noise-blocking for signal-blocking.
Closed-Loop Architecture

Right-to-Left Feedback Loops

The pipeline is not a one-way conveyor. Every right-side discovery is a missed left-side detection opportunity. Closing these loops turns the framework into a learning system.

→ Custom SAST Rule
Attack pattern discovered at runtime is codified as a custom SAST rule. Next time a developer introduces that pattern, it's caught at commit — not in production.
Example: BOLA pattern found in Noname → custom rule detects missing ownership check in code review

←
→ New TISA Test
The updated TAM threat immediately generates a TISA test candidate to validate the assumed mitigating control for the new vector.
TAM update → TISA test draft within 1 sprint

TISA Failure
Recurring control drift
←
→ SAST Rule Candidate
A TISA control that keeps failing across deploys signals a code pattern being repeatedly introduced. Evaluate whether a SAST rule can catch the root cause statically before it ever reaches TISA.

←
→ SCA Policy Tightening

Signal Source
Incident
The ultimate signal
←
→ Propagates to ALL layers simultaneously
TAM
New attack vector added. Mitigating controls reviewed for all similar threats.
SAST Custom Rule
Vulnerability class codified as static detection rule within 48h of root cause.
SCA Policy
If dependency involved, policy updated to block that component version range.
TISA Regression
Incident scenario becomes a permanent TISA test. Required within 48h of close.
The learning system principle: A security pipeline that only runs left→right finds today's vulnerabilities. One with closed feedback loops gets harder to exploit over time — each incident and runtime finding makes the static layer smarter.
